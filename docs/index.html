Bricks Import & Export

Version 1.1.1 combines Bricks native unified global transfer with a Katsarov payload for pages and supported non-template post types.

Compatibility boundary: tested target is Bricks 2.4-beta2, native schema bricks/unified-global-transfer v1. Bricks 2.4 stable requires revalidation.

Features

Schema 2 by defaultUsed only after the audited native contract verifies; otherwise export falls back to schema 1 and reports why.
No-write preflightEvery import validates the archive and produces a confirmation-bound plan before mutation.
Admin and CLIAdmin import is JavaScript-staged; WP-CLI uses the same validator, plan, and importer.
Structurally inspected native packageBricks-owned data stays inside bricks/package.zip; its structure, manifest, and hashes are checked, but native contents are not semantically rewritten.

Requirements

  • WordPress 6.0+ and PHP 7.4+.
  • ZipArchive with callable getExternalAttributesIndex() and ZipArchive::OPSYS_UNIX; this capability is checked at runtime.
  • Administrator access. Native domains can require Bricks manager permissions, uploads, SVG upload, or code-execution permission.

Coverage

Native schema 2 domains: color palettes, theme styles, classes, variables, custom fonts, icon manager, breakpoints, global queries, components, templates, settings, and custom capabilities. Templates are native-owned only.

Katsarov-owned content: ordinary pages and configured Bricks-enabled non-template post types. Missing dynamic/CPT records are skipped by default; pages may be created according to policy.

Schema-2 omissions: general media, template conditions, bricks_style_manager, global pseudo classes, and UI/workflow state including Element Manager, font favorites, and locked/trashed classes. Font/icon assets can still be included in the native package. Remote template image download is disabled.

Typed references are mapped only in known fields. Ambiguous or unresolved references block the affected page. Existing media references may be normalized, but files are never downloaded. Bricks CSS is regenerated through a verified route after import; CSS verification failures are partial and report assets in failed.

Archive schemas

Schema 1 — legacy compatibility

bricks-export.zip
├── manifest.json
├── options/
│   ├── bricks_global_settings.json
│   └── … .json
└── posts/
    ├── index.json
    ├── page__home.json
    └── bricks_template__site-header.json

Schema 1 is the exact-version legacy format and retains its raw options, template posts, and serialized legacy meta compatibility path.

Schema 2 — native transfer

bricks-export-YYYY-MM-DD.zip
├── manifest.json
├── bricks/
│   ├── package.zip
│   └── package.sha256
└── katsarov/
    ├── export-warnings.json
    └── posts/
        ├── index.json
        ├── page__home.json
        └── product__catalog-item.json

The outer manifest records the native schema and package SHA-256. Native package bytes are structurally inspected as a ZIP, including its manifest, entries, and hashes, but are not semantically rewritten. Template-condition sidecars are not applied automatically.

Usage

Admin

Open Bricks → Import & Export. Export is direct. For import, choose a ZIP, review the JavaScript preflight, acknowledge the backup and warnings, then confirm. The non-JavaScript form refuses to mutate the site.

WP-CLI

Use a real administrator identity; the plugin never chooses the first administrator.

# Export to the default date-stamped filename
wp bricks export --user=administrator

# Export to an explicit path
wp bricks export /backups/bricks.zip --user=administrator

# Export with explicitly authorized sensitive settings
wp bricks export /backups/bricks.zip --user=administrator --allow-sensitive-settings

# Preflight only
wp bricks import --file=/backups/bricks.zip --user=administrator --dry-run

# Default skip policy
wp bricks import --file=/backups/bricks.zip --user=administrator \
  --backup-acknowledged --yes

# Explicit replacement
wp bricks import --file=/backups/bricks.zip --user=administrator \
  --conflict=replace --allow-overwrite --backup-acknowledged --yes

The sole plugin-specific export flag is --allow-sensitive-settings; without it, CLI exports are redacted by default. Import flags: --file, --dry-run, --conflict=skip|replace, --allow-overwrite, --allow-sensitive-settings, --backup-acknowledged, --accept-warnings, and --yes. Dry-run never writes. Blocked, failed, partial, and cancelled imports return non-zero status.

Security and failure behavior

  • Export redaction and import authorization are separate controls. API keys, custom code, and template passwords are redacted from exports by default; explicit export opt-in is available through WP-CLI or a programmatic request.
  • On Bricks 2.4-beta2, Bricks cannot filter keys inside the native settings payload, so every incoming native settings selector requires allow_sensitive_settings. Schema 1 recursively strips nested apiKey, customCode, password, and pass keys while preserving ordinary siblings; other sensitive settings are stripped by default.
  • Imported code is not automatically approved, signed, or executed; an administrator must review it. No automatic code-signature approval occurs.
  • Preflight is mandatory; archive and plan SHA-256 hashes must match the confirmed values.
  • Conflict default is skip; replace requires --allow-overwrite or the equivalent admin confirmation.
  • Successful schema 1 and schema 2 exports replace a destination only after temporary archive close/stat and validation; failures preserve the old destination.
  • Imports use a site-wide lease and staged session cleanup. They are not full transactions; partial results distinguish core post and metadata mutations and do not claim incomplete work.

Testing

The isolated suite passes 283/283 under E_ALL. A fully disposable integration run passes on WordPress 7.0.3, Bricks 2.4-beta2, and PHP 8.4.24: schema 2 authorized replacement removes absent allowlisted Bricks meta, writes incoming meta, preserves unrelated meta, and regenerates CSS; schema 1 recursively strips nested apiKey, customCode, password, and pass while preserving ordinary siblings. It also verifies no CLI warnings or temporary ZIP leaks, frontend HTTP 200, clean logs, and cleanup. Plugin-wide PHP lint remains 24/24; Node, git-diff, and root integration checks pass. Bricks 2.4 stable, PHP 7.4 runtime execution, and builder UI interaction remain unclaimed.
